== Persistencia de Datos

El sistema utiliza dos mecanismos principales de persistencia: una base de datos relacional en PostgreSQL y una base de datos no relacional en MongoDB. Ambas se ejecutan en contenedores Docker dentro del entorno local del proyecto y cumplen funciones diferentes dentro de la arquitectura.

PostgreSQL se utiliza para almacenar la informacion estructural y principal del dominio educativo, como usuarios, tutores, estudiantes, sesiones, niveles y resultados. MongoDB se utiliza para almacenar eventos y logs generados por los servicios, permitiendo conservar informacion operativa con una estructura mas flexible.

En el entorno revisado, PostgreSQL se encuentra montado en el contenedor Docker `postgres-db`, mientras que MongoDB se encuentra montado en el contenedor `mongo-logs`.

=== Base de Datos Relacional: PostgreSQL

La base de datos PostgreSQL corresponde a la persistencia principal del sistema. En ella se almacena la informacion que requiere integridad, relaciones claras entre entidades y consistencia en las operaciones.

==== Funcion Dentro del Sistema

PostgreSQL se utiliza para guardar los datos centrales de la aplicacion. Su funcion principal es mantener informacion consistente y relacionada entre los distintos elementos del sistema.

Entre las entidades principales se encuentran:

* `admins`: usuarios administradores del sistema.
* `students`: estudiantes que utilizan la aplicacion.
* `tutors`: tutores, profesores o responsables asociados a estudiantes.
* `sessions`: sesiones de uso registradas por estudiante.
* `levels`: niveles o actividades disponibles.
* `level_results`: resultados obtenidos por los estudiantes en cada nivel.

Estas entidades mantienen relaciones entre si. Por ejemplo, un tutor puede estar asociado a varios estudiantes; un estudiante puede tener varias sesiones; y una sesion puede tener varios resultados de niveles. Este tipo de estructura requiere un modelo relacional para representar llaves primarias, llaves foraneas, restricciones e integridad referencial.

Restricciones relevantes detectadas en PostgreSQL:

* `admins.email` y `admins.username` tienen indices unicos.
* `tutors.email` tiene indice unico.
* `students.id_tutor` es una llave foranea nullable; por lo tanto, un estudiante puede existir sin tutor asignado.
* `students.gender` acepta los valores `M`, `F` u `O`.
* `tutors.gender` acepta los valores `M`, `F` u `O`.
* `tutors.degree` acepta los valores `licenciatura`, `maestria`, `doctorado`, `postdoctorado` o `padre-madre`.
* Las tablas `tutors`, `students`, `sessions`, `levels` y `level_results` usan secuencias para generar sus identificadores.

==== Justificacion del Modelo Relacional

PostgreSQL es adecuado para la informacion principal del sistema porque los datos tienen estructura definida y relaciones importantes. Los estudiantes, tutores, sesiones, niveles y resultados no son elementos aislados: dependen unos de otros y deben mantener coherencia.

El modelo relacional permite:

* Definir llaves primarias para identificar cada registro.
* Usar llaves foraneas para representar relaciones entre entidades.
* Evitar inconsistencias, como resultados asociados a sesiones inexistentes.
* Consultar informacion relacionada, por ejemplo estudiantes de un tutor o resultados de una sesion.
* Mantener reglas de integridad sobre usuarios, correos, sesiones y resultados.

Por estas razones, PostgreSQL se utiliza para los datos estructurados y criticos del dominio educativo.

=== Base de Datos No Relacional: MongoDB

MongoDB se utiliza como base de datos documental para almacenar logs y eventos generados por los servicios. A diferencia de la informacion principal del sistema, los logs pueden variar en estructura, contener metadatos diferentes y crecer continuamente conforme los servicios generan actividad.

En el entorno local revisado, MongoDB se ejecuta en Docker dentro del contenedor `mongo-logs`. La base de datos utilizada es `logsdb` y la coleccion principal es `events`.

==== Funcion Dentro del Sistema

MongoDB se encarga de almacenar informacion operativa y eventos del sistema. Los servicios pueden generar mensajes relacionados con actividad, errores, rutas consultadas, tiempos de respuesta, entidades involucradas o acciones realizadas.

El listener de RabbitMQ consume mensajes de una cola configurada, intenta interpretarlos como JSON y los guarda en MongoDB. Si el mensaje no tiene formato JSON valido, lo conserva como texto crudo mediante el campo `rawMessage`. Tambien puede agregar metadatos de RabbitMQ, como `deliveryTag`, `exchange`, `routingKey` y `redelivered`.

El servicio de logs consulta esta informacion desde MongoDB y la expone mediante endpoints HTTP y WebSocket, permitiendo al cliente administrativo revisar logs recientes, filtrarlos y consultar eventos del sistema.

==== Estructura Detectada en MongoDB

La coleccion `events` contiene documentos de logs con campos orientados a registrar actividad tecnica y operativa. La estructura detectada incluye:

* `_id`: identificador automatico del documento.
* `service`: nombre del servicio que genero el evento.
* `type`: tipo de evento, por ejemplo `success`, `error` o `event`.
* `message`: mensaje descriptivo del evento.
* `entityType`: tipo de entidad relacionada, por ejemplo `student`, `tutor`, `admin` o `null`.
* `entityId`: identificador de la entidad relacionada, cuando aplica.
* `action`: accion o metodo asociado al evento, por ejemplo `GET`, `POST` o `PUT`.
* `route`: ruta HTTP relacionada con el evento.
* `statusCode`: codigo HTTP de respuesta.
* `durationMs`: duracion de la solicitud en milisegundos.
* `timestamp`: fecha y hora del evento.
* `receivedAtUtc`: fecha y hora en que el evento fue recibido y almacenado.
* `rabbitMetadata`: objeto con metadatos de RabbitMQ.

La coleccion tambien cuenta con indices para acelerar consultas por fecha y filtros frecuentes:

* `_id_`
* `timestamp_-1`
* `service_1_timestamp_-1`
* `type_1_timestamp_-1`
* `entityType_1_timestamp_-1`

==== Justificacion del Modelo No Relacional

MongoDB es adecuado para logs y eventos porque esta informacion no siempre tiene una estructura fija. Un log puede incluir ruta, codigo de estado y duracion; otro puede incluir metadatos de RabbitMQ; otro puede representar un error; y otro puede llegar como mensaje crudo.

El modelo documental permite:

* Guardar eventos con campos variables sin modificar un esquema rigido.
* Almacenar documentos JSON de forma natural.
* Registrar metadatos adicionales conforme evolucionan los servicios.
* Consultar rapidamente eventos recientes y filtrarlos por servicio, tipo, ruta o accion.
* Separar la informacion operativa de los datos principales del dominio educativo.

Por estas razones, MongoDB se utiliza para informacion flexible, tecnica y orientada a eventos, mientras que PostgreSQL conserva los datos estructurados y relacionales del sistema.
