== JWT, Autenticacion y Autorizacion por Roles

El sistema utiliza JSON Web Token (JWT) para identificar al usuario autenticado y transportar su rol entre los clientes, el API Gateway y los microservicios. El token es generado por el microservicio de autenticacion y despues se envia en las solicitudes protegidas usando el encabezado `Authorization: Bearer`.

=== Generacion del JWT en Authentication Service

La generacion del token ocurre en el servicio de autenticacion. Cuando un usuario inicia sesion o se registra, el sistema consulta PostgreSQL para localizar la cuenta correspondiente y validar las credenciales. Las contrasenas almacenadas se comparan usando `BCrypt`.

[cols="1,3", options="header"]
|===
| Flujo
| Descripcion

| Estudiante o tutor
| El cliente llama a `POST /auth/login` o `POST /auth/register`. El servicio busca al usuario en las tablas de estudiantes o tutores y genera un token con el rol `student` o `tutor`.

| Administrador
| El cliente administrativo llama a `POST /auth/admin/login`. El servicio busca al usuario en la tabla de administradores y genera un token con el rol `admin`.

| Firma del token
| El token se firma con HMAC SHA-256 usando el secreto configurado en `Jwt:Secret`.

| Respuesta
| La respuesta incluye el `token` y el `role`. En el flujo administrativo tambien se devuelve la informacion basica del administrador.
|===

=== Informacion Incluida en el Token

El JWT contiene los datos necesarios para reconocer al usuario y su rol dentro del sistema.

[cols="1,3", options="header"]
|===
| Claim
| Uso

| `sub`
| Identificador del usuario autenticado. Corresponde al id del estudiante, tutor o administrador.

| `email`
| Correo electronico de la cuenta autenticada.

| `role`
| Rol funcional del usuario. Los valores usados por el sistema son `student`, `tutor` y `admin`.

| `iss`
| Emisor del token, configurado como parte de JWT.

| `aud`
| Audiencia esperada del token.

| `iat`
| Fecha de emision del token.

| `exp`
| Fecha de expiracion del token.
|===

=== Uso del JWT en los Clientes

Despues de recibir el token, cada cliente lo conserva y lo envia al Gateway cuando necesita consumir rutas protegidas.

[cols="1,3", options="header"]
|===
| Cliente
| Uso del token

| Cliente web
| Lee el JWT despues del login, extrae `role` y `sub`, crea una sesion por cookie y guarda el token como claim `jwt_token`. Las paginas protegidas usan autorizacion por rol, por ejemplo `student` o `tutor`.

| Cliente Android
| Guarda el token localmente, decodifica el payload para leer `role`, `email` y `sub`, y envia solicitudes protegidas con `Authorization: Bearer <token>`.

| Cliente WPF administrativo
| Valida que la respuesta del login tenga `role = admin`, conserva el token en la sesion administrativa y lo envia como `Bearer` para consultar perfil, estadisticas, logs y monitoreo.
|===

=== Papel del API Gateway

El API Gateway funciona como punto de entrada para los clientes. En las rutas protegidas, el Gateway conserva el encabezado `Authorization` recibido y lo reenvia hacia los servicios internos que requieren autenticacion.

[source,text]
----
Authorization: Bearer <jwt>
----

De esta forma, los clientes no necesitan conocer directamente la ubicacion de los microservicios internos, pero el token sigue llegando al servicio responsable de validar acceso.

=== Validacion y Autorizacion en el Microservicio de Datos

El microservicio principal de datos valida el JWT con `JwtBearer`. La validacion comprueba:

* Firma del token.
* Emisor configurado.
* Audiencia configurada.
* Expiracion del token.
* Existencia de un usuario autenticado para las rutas protegidas.

Ademas, el microservicio define politicas de autorizacion por rol.

[cols="1,2", options="header"]
|===
| Politica
| Rol permitido

| `AdminOnly`
| `admin`

| `StudentOnly`
| `student`

| `TutorOnly`
| `tutor`

| `StudentOrTutor`
| `student` o `tutor`
|===

El sistema tambien usa el helper de claims para leer el identificador y el rol del usuario desde el token. Para el identificador se usa principalmente `sub`; para el rol se usa `role`. Con esa informacion los endpoints aplican reglas adicionales, por ejemplo:

* Un estudiante solo puede consultar informacion asociada a su propio identificador.
* Un tutor solo puede consultar estudiantes asociados a su cuenta.
* Un administrador puede consultar informacion administrativa, estadisticas, logs y monitoreo.

=== Determinacion del Rol

La determinacion de si el usuario es estudiante, tutor o administrador depende del claim `role` generado por Authentication Service.

[cols="1,2,3", options="header"]
|===
| Valor de `role`
| Tipo de usuario
| Uso dentro del sistema

| `student`
| Estudiante
| Accede a su panel, perfil, tutor asignado, sesiones, resultados y actividades educativas.

| `tutor`
| Profesor, tutor o padre
| Consulta su perfil, estudiantes asignados, sesiones y resultados de sus estudiantes.

| `admin`
| Administrador
| Accede al cliente WPF administrativo, estadisticas, logs, monitoreo y gestion administrativa.
|===

En resumen, Authentication Service es responsable de emitir el token con identidad y rol; los clientes lo conservan; el Gateway lo transporta; y los microservicios lo validan para permitir o rechazar operaciones segun el rol del usuario.
