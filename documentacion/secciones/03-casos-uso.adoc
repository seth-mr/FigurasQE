== Casos de Uso

Esta seccion describe los casos de uso globales identificados a partir de los clientes y servicios del proyecto. Para efectos de la documentacion, el rol de profesor se considera dentro del perfil `tutor`, ya que en el sistema este usuario representa a la persona adulta que acompana, supervisa o da seguimiento a uno o varios estudiantes. Este rol tambien puede corresponder a padres o responsables del acompanamiento educativo.

=== Actores del Sistema

[cols="1,3", options="header"]
|===
| Actor
| Descripcion

| Estudiante
| Usuario principal de la experiencia educativa. Puede consultar su informacion, su tutor asignado, sus sesiones y sus resultados de actividad.

| Profesor / Tutor / Padre
| Usuario responsable del seguimiento de estudiantes. Puede consultar su perfil, asociar estudiantes y revisar informacion, sesiones y resultados de los alumnos asignados.

| Administrador
| Usuario encargado de supervisar la operacion general del sistema. Puede iniciar sesion en el cliente administrativo, consultar estadisticas, revisar logs, monitorear servicios y gestionar su informacion administrativa.
|===

=== Casos de Uso del Estudiante

[cols="1,2,4", options="header"]
|===
| ID
| Caso de uso
| Descripcion

| CU-E-01
| Registrarse como estudiante
| El estudiante puede crear una cuenta proporcionando sus datos personales y credenciales de acceso. El registro permite identificarlo dentro del sistema y asociar posteriormente su actividad educativa.

| CU-E-02
| Iniciar sesion
| El estudiante puede iniciar sesion con correo y contrasena. Al autenticarse, el sistema genera un token que permite reconocer su identidad y rol.

| CU-E-03
| Acceder al panel del estudiante
| El sistema dirige al estudiante a su pantalla principal, donde puede consultar un resumen de su informacion, sesiones registradas y estado general de su actividad.

| CU-E-04
| Consultar informacion personal
| El estudiante puede visualizar sus datos registrados, como nombre, edad, genero, pais, correo y condicion de neurodivergencia cuando aplique.

| CU-E-05
| Consultar tutor asignado
| El estudiante puede revisar la informacion del tutor asociado a su cuenta, cuando exista una asignacion registrada.

| CU-E-06
| Consultar sesiones de uso
| El estudiante puede consultar el historial de sesiones asociadas a su cuenta, incluyendo fechas, dispositivo y datos relacionados con la actividad.

| CU-E-07
| Consultar resultados de niveles
| El estudiante puede consultar resultados asociados a sus sesiones, como niveles completados, intentos, fallos, tiempo de finalizacion y estado de completado.

| CU-E-08
| Jugar nivel
| El estudiante puede realizar una actividad o nivel dentro de la aplicacion. Durante este proceso, el sistema registra la sesion de uso y guarda los resultados obtenidos, como intentos, fallos, tiempo de finalizacion y estado de completado.

| CU-E-09
| Cerrar sesion
| El estudiante puede cerrar su sesion para finalizar el acceso activo a la aplicacion.
|===

=== Descripcion Detallada de Casos de Uso Principales

Los siguientes casos de uso detallan los flujos mas importantes del sistema y se derivan de los casos ya definidos en las tablas anteriores. Cuando una misma funcion existe para mas de un rol, se agrupa en una sola descripcion para evitar repetir el mismo comportamiento tecnico.

==== CU Principal 01: Iniciar sesion

[cols="1,3", options="header"]
|===
| Elemento
| Descripcion

| Actores
| Estudiante, Profesor / Tutor / Padre y Administrador.

| Precondiciones
| El usuario debe existir en el sistema. El API Gateway, el microservicio de autenticacion y PostgreSQL deben estar disponibles. El cliente debe conocer la URL del Gateway.

| Postcondiciones
| El usuario queda autenticado. El cliente conserva el token JWT recibido y puede consumir las funciones permitidas por su rol.

| Flujo principal
a|
. El actor ingresa correo y contrasena en el cliente correspondiente.
. El cliente envia la solicitud al API Gateway.
. El Gateway redirige la peticion al microservicio de autenticacion.
. El microservicio valida las credenciales contra PostgreSQL.
. Si las credenciales son correctas, el sistema genera un token JWT con identidad y rol.
. El token se devuelve al cliente.
. El cliente dirige al usuario hacia las funciones permitidas para su rol.

| Flujos alternos
a|
* Si el actor es estudiante o tutor, el inicio de sesion se realiza mediante el flujo general de autenticacion.
* Si el actor es administrador, el inicio de sesion se realiza mediante el flujo administrativo y el sistema valida que el usuario tenga rol de administrador.

| Flujos de excepcion
a|
* Si las credenciales son incorrectas, el sistema rechaza el acceso.
* Si el usuario no existe, el sistema responde con error de autenticacion.
* Si el token no puede generarse, el sistema no inicia sesion.
* Si el Gateway, el servicio de autenticacion o PostgreSQL no estan disponibles, el cliente muestra un error de conexion o servicio.
|===

==== CU Principal 02: Registrar usuario

[cols="1,3", options="header"]
|===
| Elemento
| Descripcion

| Actores
| Estudiante y Profesor / Tutor / Padre.

| Precondiciones
| El usuario no debe estar registrado previamente con el mismo correo. El API Gateway, el microservicio de autenticacion y PostgreSQL deben estar disponibles.

| Postcondiciones
| Se crea la cuenta del usuario con el rol correspondiente. El usuario queda disponible para iniciar sesion o continuar el flujo de autenticacion definido por el cliente.

| Flujo principal
a|
. El actor abre el formulario de registro.
. El actor captura sus datos personales y credenciales.
. El cliente envia la informacion al API Gateway.
. El Gateway redirige la solicitud al microservicio de autenticacion.
. El microservicio valida los datos recibidos.
. El sistema verifica que el correo no exista previamente.
. El sistema guarda la cuenta en PostgreSQL con el rol correspondiente.
. El sistema responde confirmando el registro.

| Flujos alternos
a|
* Si el actor se registra como estudiante, la cuenta se crea con el rol de estudiante.
* Si el actor se registra como tutor, profesor o padre, la cuenta se crea con el rol de tutor.

| Flujos de excepcion
a|
* Si faltan campos obligatorios, el sistema rechaza la solicitud.
* Si el formato de los datos no es valido, el sistema devuelve error de validacion.
* Si el correo ya existe, el sistema no crea una cuenta duplicada.
* Si PostgreSQL no esta disponible, el sistema no registra la cuenta.
|===

==== CU Principal 03: Consultar progreso del estudiante

[cols="1,3", options="header"]
|===
| Elemento
| Descripcion

| Actores
| Estudiante y Profesor / Tutor / Padre.

| Precondiciones
| El actor debe haber iniciado sesion. El token JWT debe ser valido. El Gateway, el microservicio de datos y PostgreSQL deben estar disponibles.

| Postcondiciones
| El actor visualiza informacion de progreso permitida por su rol. No se modifican datos al realizar la consulta.

| Flujo principal
a|
. El actor solicita consultar informacion de progreso.
. El cliente envia la peticion al API Gateway con el token JWT.
. El Gateway redirige la solicitud al microservicio de datos.
. El microservicio valida la identidad y el rol del actor.
. El servicio consulta PostgreSQL.
. El sistema devuelve informacion de perfil, tutor, estudiantes asignados, sesiones o resultados segun corresponda.
. El cliente muestra la informacion al actor.

| Flujos alternos
a|
* Si el actor es estudiante, solo puede consultar informacion asociada a su propia cuenta.
* Si el actor es tutor, profesor o padre, solo puede consultar estudiantes asociados a su cuenta.
* Si el tutor filtra sesiones por periodo, el sistema limita los resultados al rango solicitado.

| Flujos de excepcion
a|
* Si el token esta ausente, expirado o es invalido, el sistema rechaza la consulta.
* Si el actor intenta consultar informacion fuera de sus permisos, el sistema niega el acceso.
* Si no existen registros de sesiones o resultados, el sistema devuelve una respuesta vacia o sin datos.
* Si el microservicio de datos o PostgreSQL no estan disponibles, el cliente muestra un error de servicio.
|===

==== CU Principal 04: Jugar nivel

[cols="1,3", options="header"]
|===
| Elemento
| Descripcion

| Actores
| Estudiante.

| Precondiciones
| El estudiante debe haber iniciado sesion. El cliente debe contar con un token JWT valido. El Gateway, el microservicio de datos y PostgreSQL deben estar disponibles. Para actividades con deteccion de manos, tambien debe estar disponible HandsDetection.

| Postcondiciones
| La actividad queda reflejada como sesion de uso y resultado de nivel cuando el flujo se completa correctamente. El avance puede consultarse posteriormente por el estudiante o por su tutor.

| Flujo principal
a|
. El estudiante inicia un nivel o actividad desde el cliente.
. El cliente ejecuta la experiencia interactiva del nivel.
. Si la actividad requiere deteccion de dedos, el cliente envia la imagen al API Gateway mediante la ruta `/hands`.
. El Gateway envia la imagen al servicio HandsDetection mediante gRPC.
. HandsDetection procesa la imagen y devuelve el conteo de dedos detectado.
. El cliente utiliza la respuesta para continuar la actividad.
. Al finalizar, el cliente envia los datos de sesion o resultado al API Gateway.
. El Gateway redirige la informacion al microservicio de datos.
. El microservicio valida la solicitud y guarda la sesion o resultado en PostgreSQL.
. El sistema confirma el registro del avance.

| Flujos alternos
a|
* Si el nivel no requiere deteccion de manos, el flujo continua sin invocar HandsDetection.
* Si el estudiante no completa el nivel, el sistema puede conservar solo la informacion de sesion o no registrar resultado completado, segun la informacion enviada por el cliente.

| Flujos de excepcion
a|
* Si el token del estudiante es invalido, el sistema rechaza el registro.
* Si HandsDetection no responde, la actividad que depende de deteccion de manos no puede obtener el conteo esperado.
* Si los datos de sesion o resultado son invalidos, el microservicio de datos rechaza la solicitud.
* Si PostgreSQL no esta disponible, el avance no puede persistirse.
|===

==== CU Principal 05: Consultar logs y monitorear servicios

[cols="1,3", options="header"]
|===
| Elemento
| Descripcion

| Actores
| Administrador.

| Precondiciones
| El administrador debe haber iniciado sesion en el cliente WPF. El token JWT debe ser valido. El Gateway y los servicios consultados deben estar disponibles para responder.

| Postcondiciones
| El administrador visualiza logs, eventos o estado de servicios. La consulta no modifica informacion del sistema.

| Flujo principal
a|
. El administrador abre el cliente WPF.
. El administrador inicia sesion mediante el API Gateway.
. El administrador entra a la seccion de logs o monitoreo.
. El WPF consulta al API Gateway usando el token JWT.
. Para logs, el Gateway redirige la consulta al Logs Service.
. El Logs Service consulta los eventos almacenados en `mongo-logs`.
. Para monitoreo, el Gateway consulta el endpoint de salud del servicio solicitado.
. El WPF muestra logs, filtros, eventos en tiempo real o tarjetas de estado segun la accion seleccionada.

| Flujos alternos
a|
* El administrador puede consultar logs generales o filtrarlos por servicio.
* El administrador puede recibir eventos de logs en tiempo real mediante WebSocket.
* El administrador puede consultar el estado de Gateway, Auth Service, microservicio de datos, Logs Service, RabbitMQ Mongo Listener, MongoDB, PostgreSQL y HandsDetection.

| Flujos de excepcion
a|
* Si el token del administrador es invalido, el sistema rechaza la consulta.
* Si Logs Service no esta disponible, el WPF no puede cargar los logs.
* Si `mongo-logs` no esta disponible, Logs Service no puede recuperar eventos.
* Si RabbitMQ o el listener estan detenidos, pueden dejar de persistirse nuevos eventos.
* Si un servicio no responde al monitoreo, el WPF lo muestra como no disponible o con error.
|===
